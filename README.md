# Student Registry

A focused student registry application for a technical assessment.

## Scope

The application supports four workflows:

1. Create and manage student records.
2. Assign programme fees and record payments.
3. Create assessments and accept student submissions.
4. Grade submissions and publish results.

The required stack is Next.js App Router, TypeScript, PostgreSQL
and Prisma. PostgreSQL and private file storage will use Supabase.

## Access and demo experience

The application has two roles: Staff and Student.

Authentication is outside the initial scope. A clearly labelled demo
selector lets reviewers enter as staff or choose a seeded student.

Server-side checks enforce the selected role and student ownership.
The selector is for demonstration and is not secure authentication.
All demo records will use fictional data.

A repeatable seed script will provide at least five students,
two programmes, assigned fees, payments, assessments and sample grades.

## Product decisions

### Students

- Supported statuses: Enrolled, Deferred, Withdrawn and Completed.
- Student IDs are generated by the server and unique in the database.
- Student emails are trimmed, normalised and unique.
- Students can be searched by name or ID and filtered by programme
  and status.

### Fees and payments

- A student's assigned fee records the programme price at assignment.
- Later programme price changes do not alter existing assigned fees.
- Each assigned fee has a due date.
- Outstanding balance is calculated from the fee and recorded payments.
- A positive outstanding balance becomes overdue after its due date.
- Payments must be positive and cannot exceed the outstanding balance.

### Assessments and submissions

- Assessments belong to a programme and academic year.
- Students can access assessments matching their enrolment.
- Accepted file formats are PDF and DOCX, with a 10 MB size limit.
- Each student has one current submission per assessment.
- Resubmission replaces the current file and is allowed only before
  the deadline.
- First submissions at or after the deadline are accepted and flagged
  as late.
- Resubmissions at or after the deadline are rejected.
- Server time determines whether the deadline has passed.
- Files are private and downloads require an access check.

### Results

- Staff can grade submitted assessments from 0 to 100.
- Classification: Fail below 40, Pass from 40, Merit from 60,
  and Distinction from 70.
- Publication is controlled per student assessment result.
- Students only receive published grades.
- Editing a published grade withholds the result until republished.

## Form handling and validation

- TypeScript strict mode is enabled; explicit `any` is prohibited.
- React Hook Form manages interactive forms.
- Zod schemas are connected through zodResolver for client validation.
- The server independently validates incoming requests with Zod.
- Input schemas are shared where client and server contracts match.
- TypeScript input types are inferred from schemas.
- Server-side role and ownership checks protect operations and data.
- Database-dependent rules are enforced in server-side operations.
- Reusable form components provide consistent labels, errors,
  accessibility and submission states.

## Implementation plan

1. Application foundation and quality checks.
2. Database schema, migrations, seed data and demo access.
3. Student enrolment and search.
4. Fees, payments and overdue dashboard.
5. Assessments and file submissions.
6. Grading and result publication.
7. Testing, deployment verification and reviewer documentation.

Each milestone will be committed after its behaviour is verified.

## Out of scope

- Production authentication and account registration.
- Additional administrative roles.
- Payment gateway integration.
- AI grading or chatbot features.
- A full learning management system.

## AI assistance

AI has been used across the development process:
- Initial project analysis, requirement scoping, and data model drafting.
- Student directory implementation: Designing search parameter handling, index-backed exact student ID lookup vs case-insensitive name matching, and Partial Prerendering Suspense boundaries.
- Student enrolment workflow: Designing shared Zod validation (date-only calendar checks, non-future DOB, consecutive academic year format), atomic transaction boundary for `Student` and `FeeAssignment` creation, server-side derivation of calendar `enrolmentYear` (assigning SMS-2026-… for enrolments entered in 2026 even when backdated to 2025/2026), read-only fee display with `useWatch`, and mapping PostgreSQL uniqueness conflicts (`P2002`) to HTTP 409 for concurrency safety.
- Code review and verification: Running automated validation scripts and ensuring strict TypeScript compliance without explicit `any`.
